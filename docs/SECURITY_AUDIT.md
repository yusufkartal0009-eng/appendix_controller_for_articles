# Security audit of the container execution boundaries (#46)

> Evidence document. The table is generated by `scripts/security_audit.py` from `data/security_audit/results.json`;
> the findings below it are written from that table. Anything not tried is listed under "Not tested".

## 1. Scope and method

Paper code runs in a Docker container started by `src/sandbox/runner.py` (`build_docker_command`). The audit runs
probe programs **through that same runner on the owner's machine** (Windows 11, Docker Desktop with WSL2), so each
probe gets exactly the flags of a paper run: `--network none`, `--read-only`, tmpfs mounts with `noexec`,
`--security-opt no-new-privileges`, `--user 1000:1000`, `--cpus`, `--memory`, `--memory-swap`, `--pids-limit`.
A control **holds** (PASS) when the hostile attempt fails; FAIL means the control is missing or broken; INFO is
behavior that is recorded and is not a control.

    python scripts/security_audit.py          # run every probe (needs Docker and the sandbox image), rewrite the table
    python scripts/security_audit.py --check  # fail if the table below is not what results.json renders to

The first run, before any fix, is kept in `data/security_audit/results_before_fixes.json`.

## 3. Findings

| ID | Finding | Severity | Status |
|---|---|---|---|
| F-1 | The capability bounding set still holds Docker's 14 default capabilities (`--cap-drop ALL` is missing). Not usable today: the process is uid 1000 with no effective capabilities, `no-new-privileges` is set, and the `chroot`, `mknod`, raw socket, `mount`, and `setuid` attempts were all refused. | Low (defense in depth) | **Fixed** in #260: `--cap-drop ALL` is in the run command, the bundling command, and the compose file. After the fix the audit shows `CapBnd=0` (row 3); the 20 sandbox acceptance checks pass again (3.11 image) and `scripts/gpu_check.py` still sees the GPU. |
| F-2 | The output directory is a bind mount of a host folder without a quota: 512 MiB written by a run landed on the host disk. | Medium (a runaway or hostile paper can fill the host disk within its time limit) | **Fixed** in #261 (option 2 of the issue): the runner measures the output directory every 0.5 s and kills the container above `SandboxConfig.output_limit_mb` (default 1024 MiB, 0 = off); the run gets the status `OUTPUT_LIMIT_EXCEEDED`. Not a hard bound: a fast writer gets past the limit before the kill. Measured on the real runner with a 4096 MiB writer, 3 runs each: limit 64 MiB left 149 to 186 MiB on the host disk, limit 256 MiB left 274 to 295 MiB, limit 1024 MiB left 1053 to 1056 MiB (18 to 122 MiB over). The audit row 42 allows 512 MiB over. The kill is by the host, so the paper cannot stop it. A sparse file counts with its apparent size. |
| F-3 | A paper can kill its own watchdog (`timeout`, same uid); the container then ends at once and the run is reported as `TIMEOUT` although the limit was not reached. Still bounded; wrong label only. | Low | Issue #262, not started |
| F-4 | The bundling container (`RepoStager._docker_pip_command`, `pip download`) has the network on by design and runs binary-only downloads, so no package code runs; it also lacks `--cap-drop ALL`, `--read-only`, and memory and process limits. **Read from the code, not probed at run time.** | Low | Capability drop done in #260 (checked by a direct run with the real command: `CapBnd=0`, and `pip download` of a wheel still works); `--read-only` and memory and process limits are not done |

Observations that are not findings:

- The output directory is writable on purpose (logs and metadata). Symbolic links created there (`link_*` rows) appear
  on this Windows host as reparse points that the host cannot read (`OSError` errno 22), so host code reading the
  output folder does not follow them here. On a Linux host they would be real symbolic links; the runner reads only
  files it names (`execution_meta.json` and the logs), but this was **not** tested on Linux.
- `GPG_KEY` is set in the environment by the official `python` image; it is the public key ID that signs CPython
  releases, not a secret, and the probe ignores it.
- `/proc/kcore` can be opened but reads as empty: Docker masks it with `/dev/null`.

## 4. Not tested

- Kernel or container-runtime vulnerabilities (a patched Docker Desktop and WSL2 kernel are assumed; versions are in
  the table header and `data/pilot2_runs/environment.txt`). No exploit code was tried.
- The GPU run (`--gpus`): the same flags apply, but no escape probe ran with a GPU attached.
- The Python 3.8 and 3.9 images and the `-build` images (they share the Dockerfile and the runner command).
- A Linux host (Docker without Desktop), and rootless Docker.
- The host side: how the runner and `src/` code treat a hostile output folder beyond the symbolic-link check above.
- Side channels, and a long-running denial of service on the host beyond the limits probed here.
