# Installed-environment cache: two runs of paper_003 (#380)

Status: **measured**, see sections 3 and 4. Decision and safety reasoning: `docs/DECISIONS.md` D-010.

## 1. What was run

`paper_003` (FT-Transformer on California Housing) with the settings of the Pilot 3 overlay, 50% of the host's RAM and 2 CPUs
(`--pilot3 --memory 50%`, as in `docs/MEMORY_RUNS.md`), twice in a row, sequentially, with `--env-cache .sandbox_cache/env`:

    python scripts/run_pilot.py paper_003 --pilot3 --memory 50% --env-cache .sandbox_cache/env --record-root data/env_cache_runs/first_run
    python scripts/run_pilot.py paper_003 --pilot3 --memory 50% --env-cache .sandbox_cache/env --record-root data/env_cache_runs/second_run

The first run finds no entry, installs as usual and stores the result. The second run finds the entry, verifies its digest,
skips the install container and mounts the stored directory read-only. Both are **not protocol runs** (the record says so).
The earlier runs of the same paper with the same settings but no cache are the references.

## 2. The pip download cache

The bundling step already used a persistent cache before this change: `src/sandbox/stager.py` runs `pip download` inside the
sandbox image with `PIP_CACHE_DIR=/staging/.pip-cache`, a directory shared by all papers inside the staging directory. This
change leaves it as it is. Its effect is visible in the "Bundling" column below (the bundling time of the later runs).

## 4. What this does and does not show

Read from the table above (nothing here is a claim beyond it):

- **Measured:** the install phase of the second cached run took 179 s where the two earlier runs without the cache took 1,055 s
  and 1,000 s, and the first cached run (which installs and stores) took 1,051 s. The saving of the install phase is therefore
  about 820 to 876 s, and the whole run (staging, bundling, install, run) was about 906 to 1,111 s shorter (1,549 s against
  2,455 s and 2,660 s).
- **The remaining 179 s are the cache's own cost:** `env_cache.json` of the second run says 177 s went into reading and hashing
  the stored environment (47,206 files, 4.998 GB) to verify it before use; the hash of the bundle for the key is the rest. The
  verification is what makes a stored environment safe to reuse (D-010); it is the largest remaining part of a hit.
- **The first run with the cache is not faster:** it installs as usual and then spends 268 s copying the environment into the
  cache (`stored.store_seconds`). Its whole run took 2,839 s against 2,455 s and 2,660 s without the cache. The cache pays off
  from the second run of the same locked package list.
- **The run phase is not made shorter by the cache and no gain is claimed for it.** The run phase of the second cached run
  (1,306 s) is shorter than the references (1,391 s and 1,497 s), but the two references already differ by 107 s from each other
  and the cache does not touch that phase; the difference is within the spread of repeated runs of this paper, not a result.
- **Same results:** status `COMPLETED`, exit code 0 and the metrics `{"loss": 0.106, "rmse": 0.473}` are the same in all four runs.
  This says the cache did not change what the run reports for this paper; it is one paper and one run with a hit.
- **Not measured:** other papers; a cache hit under memory pressure; the effect of the 5 GB per environment on disk; how the
  verification time grows with a larger environment; whether the 106 s spread of the run phase comes from the machine or the
  paper (seed stability is not measured here either).
- **The clock was not quiet during the first cached run.** Short test suites and lint runs (about 15 s each, several times), the
  three-pass extraction of `docs/AUTO_CONSENSUS.md` (network calls and PDF parsing), and the article selection of
  `docs/EXTERNAL_VALIDATION.md` (downloads and PDF parsing, about 4 minutes each, three times) ran on the same machine while
  it was running. During the second cached run (02:36 to 03:01) only waiting commands ran. The first run's times therefore carry
  more noise than the second's, and differences of a few percent are not significant.
- The cache directory (`.sandbox_cache/`, 5 GB for this one environment) is not committed.
