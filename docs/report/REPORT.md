## 1. Abstract

Repro Radar is a pilot tool that tries to reproduce published results mechanically: it runs a paper's
released code at a pinned commit in an isolated Docker sandbox, extracts the paper's own numerical claims with a
quote check, and scores it on a four-tier rubric. We applied it to six tabular
papers in three pilots, one counted run per paper, and then to six further papers in a fourth pilot.

## 2. Introduction

Reproducibility in empirical machine learning rests on being able to re-run a published result from the paper
and its code. The point is not new: Claerbout argued in the early 1990s that a computational result's real
scholarship is the full software environment that produced it, not the paper describing it [1]; Buckheit and
Donoho later put this plainly, that an article is advertising for the scholarship, the scholarship itself is the
code and data [2, 3]. Tool and practice collections followed [4], and so did evidence that the problem had not
gone away: a 2016 *Nature* survey described a "crisis" in research reproducibility across fields [5], and a 2019
NeurIPS program examined the state of reproducibility in machine learning specifically [6]. In deep
reinforcement learning, reproducing a published result is "seldom straightforward," because results vary with
non-deterministic benchmark environments and with variance intrinsic to the methods themselves [7] — the same
caution applies more broadly: a result can differ between runs for reasons that have nothing to do with whether
the original claim was sound.

This project's own seed corpus illustrates the problem at a small scale. Of the first 16 numerical claims
recorded from 6 papers, only 2 could be found, as printed, in the paper they were attributed to; the rest were
either not present or attached to the wrong paper or table (`docs/CORPUS_VERIFICATION.md`). Two of the six
repositories had been renamed or had a target script removed by a later rewrite of the project they belong to.
Re-running a paper is therefore not only a matter of running code: it requires reconstructing the right
environment, the right version of the code, and the right data, and checking numbers against the paper itself
rather than against a value someone wrote down from memory.

Repro Radar is an attempt to do this mechanically and honestly for a small set of tabular machine learning
papers: stage each paper's code at a pinned commit, run it inside an isolated sandbox whose isolation properties
are checked against a real Docker daemon in continuous integration (`docs/SANDBOX_ACCEPTANCE.md`), extract the
paper's own numerical claims with a verbatim-quote guard against invented matches, and score the result on a
four-tier rubric instead of a single pass/fail. As of this writing, the sandbox and the corpus verification are
checked, the six papers of the corpus have been run through the sandbox in three pilots (section 6), and
`cli.py score` scores a stored real run against accepted claims (`docs/gap_analysis.md`, finding GA-2, closed by
#136); but no run has been shown to reproduce an accepted claim, so the scoring rubric's agreement tier has not yet been exercised
on real results (sections 6.3 and 6.11). The stability tier has been exercised on real seed runs of two of the papers (section 6.4a). The seed pilots cover tabular
ML benchmarks only; the later pilot, the candidate lists and the automatic search drift to other kinds of papers (sections 6.5, 6.8 and
6.10), but no claim is made about other scientific fields.

## 3. Related work

Work on reproducibility in machine learning can be grouped by what it measures: how well papers document their
experiments, whether independent re-implementation works, whether released code runs, and how much results vary
from run to run.

**Documentation and re-implementation.** Gundersen and Kjensmo surveyed 400 papers from IJCAI and AAAI with six
reproducibility metrics; none of the papers documented all the variables needed to reproduce its results, and between
20% and 30% of the variables for each factor were documented [8]. Raff attempted to implement 255 papers published
between 1984 and 2017, without looking at the authors' code, and analyzed the recorded features of each paper
statistically, on the argument that releasing code is important but not sufficient for determining reproducibility [9].
At the level of a community, the NeurIPS 2019 reproducibility program combined a code submission policy, a
reproducibility challenge, and a reproducibility checklist in the submission process [6]. Collberg and Proebsting argue,
for computer systems research, for funding repeatability engineering and rewarding the sharing of research
artifacts [10].

**Executing released code.** The studies closest to Repro Radar's question run code that authors have released.
Trisovic et al. executed R code from more than 2,000 replication datasets in a clean runtime environment: 74% of the R
files failed to complete without error in the first execution, and 56% still failed after automatic code cleaning [12].
Pimentel et al. report a large-scale study of the quality and reproducibility of Jupyter notebooks [11]. Boettiger
examines why code written for one research project often cannot be run or extended by later researchers, and
presents Docker as one way to address this [13]. Repro Radar also uses containers, but as an isolation boundary for
code it does not trust as well as for repeatability (section 4.1).

**Variance.** Henderson et al. show, for deep reinforcement learning, that non-determinism in benchmark environments
together with variance intrinsic to the methods can make reported results hard to interpret [7]. Bouthillier et al.
model the benchmarking process and find that data sampling, parameter initialization, and hyperparameter choice each
affect results markedly [14]. These results motivate Tier 3 of the score, stability across seeds (section 4.2); the
counted pilot runs were single runs, and the seed runs of section 6.4a are what exercise that tier.

**Where Repro Radar sits.** Compared with the large studies above, Repro Radar is small and deep: six tabular machine
learning papers chosen by the project, not sampled, each at a pinned commit, run in an isolated sandbox with a setup
written by the project, and judged against numbers that a person accepted after a verbatim-quote check. It does not
estimate how reproducible a field is, and its counts are not comparable with those of [12]: other language, other
selection, far smaller n. What it contributes is a method and a measured list of what stops a paper from installing
and running (section 6).

- **Sources:** [6]–[14]. [6] and [7] were verified earlier (`docs/INTRODUCTION_SOURCES.md`); every source and every

## 4. Method

### 4.1 Sandbox and threat model

Third-party paper code is untrusted by construction: it is run once, usually without being read first. Every
run happens inside a Docker container built from `docker/Dockerfile.sandbox`, under a non-root user (uid 1000,
verified check 1 of `docs/SANDBOX_ACCEPTANCE.md`), with the network disabled (`--network none`, check 2), the
root filesystem read-only (check 3), and `/tmp` and the user's home directory as size-limited `tmpfs` mounts
(2048 MiB, `noexec` on `/tmp`; `docs/DECISIONS.md` records why the home directory itself needs `exec` for
compiled extensions it loads). Resource limits are enforced and checked against real load: 2 CPUs (check 17),
6–8 GiB of memory with the container killed and the kill reported as `OOM_KILLED` rather than confused with a
timeout (checks 8 and a dedicated acceptance test), 100 processes (check 9), and a wall-clock timeout per phase
(check 4). Dependencies are installed from pre-downloaded binary wheels only — building a source distribution
would run arbitrary `setup.py` code outside the sandbox, so source-only packages are either built inside a
separate, identically isolated build-phase container (check 18) or flagged `NEEDS_SDIST_BUILD` and not built at
all (`docs/gap_analysis.md`, GA-22). A GPU is never attached unless explicitly requested (check 20) and is never
part of the counted pilot run (`docs/PILOT_2.md` section 3); one run of a synthetic paper with the GPU attached is reported in
section 6.4a. Running without Docker at all is refused by
default; an explicit, logged opt-in is required to fall back to an unisolated local run (check 6). The container
shares the host kernel, so these measures reduce, not eliminate, the risk of running unknown code — this is a
property of container isolation generally, not specific to this project.

### 4.2 Reproducibility score

Each run is scored on four weighted tiers (`src/config.py`): **Tier 1**, build and install success, 35%; **Tier
2**, agreement between the paper's claimed metrics and the reproduced ones, 35%; **Tier 3**, stability across
repeated runs with different seeds, 15%; **Tier 4**, documentation and license completeness, 15%. The composite
score classifies a paper as `Verified` (≥ 85), `Partially Verified` (60–84), or lower tiers below that
(`src/scoring.py`).

Tier 2 compares each claimed metric with the reproduced one using a single default tolerance of 5%
(`DEFAULT_TOLERANCE`, `src/config.py`), applied in `src/scoring.py`: a reproduced value within 5% relative
error earns full points; for a metric claimed inside [0, 1] (accuracy, AUROC, F1) an absolute difference of up
to 0.05 also counts; within twice the tolerance earns half the points; beyond that, none. Runtime and latency
metrics, recognized by name, are judged by relative error only, because an absolute bound would let 0.02 s
become 0.06 s, a 200% error, and still pass. The scorer has no per-category tolerance (for example a tighter
bound for AUROC than for accuracy) and does not separate a hardware difference from a real divergence; a module
that was meant to do this was never connected to the scorer and was removed (#254). The comparison of two runs in the
diagnosis layer (section 6.7) lists recorded differences and sizes a metric shift, but the scorer does not use it. A claim is matched with
the run's metrics by exact name; `cli.py score` keys a claim by its question ID, which is not the name the metric extractor gives the
metric, so a real claim is reported as not found (section 6.11).
Tier 3's stability check uses the coefficient of variation (CV) across seeds: CV ≤ 2% is
scored as deterministic, ≤ 5% as stable, with the score falling as the variance grows. Since #48 a paper that has a seed
parameter of its own is run once per seed (`docs/MULTI_SEED.md`, `scripts/run_multi_seed.py`); the metric with the largest CV
among the metrics found in every successful seed run decides, and a paper without two successful seed runs keeps the
single-run baseline of 75.0, which is a placeholder and not a measurement.

### 4.3 Claim extraction

A claim is one number a paper reports for one metric, one dataset, one model, and one split, defined precisely
in `docs/CLAIM_SCHEMA.md` (W1, #129): the value is kept exactly as printed (`value_as_printed`, including `%`,
`±`, and any stray spacing inside the number) alongside a normalized value computed by `src/claim_schema.py`,
never typed by hand. Extraction reads the PDF's page text, cached by the file's hash (W2, #130,
`docs/PDF_TEXT_EXTRACTION.md`). No API key is currently used (decision D-004, `docs/DECISIONS.md`); instead, an
agent reads the paper text under a fixed set of rules and answers one prepared question per claim
(`docs/AGENT_EXTRACTION.md`): answer only from the given text, never guess or borrow a value from a similar
dataset or metric, and answer `not_found` with a reason when the paper does not report it. Two extraction passes
are compared by normalized value (D-005); every claim's quote must also occur verbatim in the page text,
checked by the quote guard (W4, #132, `src/quote_guard.py`) — a claim whose quote cannot be found is rejected,
not silently dropped. Accepted claims are stored with their page, quote, and extraction method (W6, #10), and
nothing reaches scoring until a person has reviewed it one by one (W7, #134, `src/claim_review.py`,
`python cli.py review-claims`). Measured against the project owner's own gold set of 18 questions over 6 papers,
this pipeline reached precision 1.0 and recall 1.0 (W5, #133, `data/claims/gold_score_pass_A.json`), including
two cases built specifically to catch a fabricated match: a dataset name ("EP3602") and a metric ("HIGGS") that
do not occur in their papers at all, both correctly answered `not_found`.

## 5. Experimental setup

### 5.1 Corpus

The seed corpus went through two corrections before reaching its current 6 papers. The first 18 entries,
written in Week 1, were placeholders that in several cases paired a paper's title with an unrelated
general-purpose library's repository (`docs/PROGRESS.md`). These were replaced by 8 entries on 2026-09-13, but
that replacement was itself called "verified" without every entry having actually been checked; a later review
found only one paper had been (`docs/PROGRESS.md`, the 18→8 note). Two further entries were then dropped as
not fixable, leaving the 6 papers scored in `docs/CORPUS_VERIFICATION.md` today: TabPFN, FT-Transformer, TabR,
FastSK, SAINT, and DANet, each pinned to one commit of its repository.

An automated check (`scripts/verify_corpus.py`, run in CI on every push) verifies, for every entry, that the
paper title matches its arXiv or Crossref record, that the repository exists, that its declared license matches
GitHub's own license detection and is on an allow-list of open licenses, and that the pinned target script
exists at the pinned commit. As of the last recorded run, 6 of 6 entries pass this check. Passing it proves the
links, license, and script file are real; it does not prove the script runs or reproduces the paper's numbers —
each entry's row in `docs/CORPUS_VERIFICATION.md` separately tracks GPU requirements, whether its data must be
downloaded, and how many of its recorded claims could actually be found in the paper (as low as 0 of 3 for one
entry). No entry in the corpus is called "verified" as a whole; every one still carries at least one open,
explicitly marked item.

### 5.2 Sandbox limits and run setup

Every run, in both pilots, uses the same fixed resource limits: 2 CPUs, 6 GiB of memory (6 GiB swap), 100
processes, and a 3600-second timeout per phase (build, install, run), with the network disabled throughout
(`docs/PILOT_2.md` section 3). The first pilot (Pilot 1, `docs/PILOT_WEEK2.md`) ran each paper's script directly
from the repository root with no paper-specific adjustment; it showed that no paper reached its own experiment
code this way (full accounting in section 6). Each paper's `run_setup` in `data/seed_papers.json` now records,
individually, the fix that pilot found necessary: the entry command (several papers are driven through a
Jupyter notebook via `nbconvert`, not a plain script), the working directory, whether the repository needs a
writable per-run copy, which datasets must be fetched to a local cache before the run (since the sandbox has no
network), and which packages must be built from source inside an isolated build phase rather than installed as
a published wheel. This is also where each paper's Python version comes from (3.8, 3.9, or 3.11, chosen from
its own README or environment file) and where any extra install-time requirements or version constraints are
recorded, each with the reason and source for the choice next to it — not applied silently.

### 5.3 Success definitions

Three outcomes are defined precisely and used consistently across both pilots (`docs/PILOT_WEEK2.md` section
"Definitions"):

| Term | Definition |
|---|---|
| Install success | `dependency_install_status: INSTALLED` in the run report. `FAILED`, `SKIPPED` (nothing to install), and `UNKNOWN` do not count. |
| Run success | Exit code 0 of the run phase, in a run that was actually valid (staged at the pinned commit, isolated, Docker used). `TIMEOUT`, `OOM_KILLED`, and any other non-zero exit code do not count. |
| Pilot success | Install success **and** run success, together. |

Every rate (install success rate, run success rate, pilot success rate) is reported with a denominator of 6 —
every paper in the corpus, including one whose staging or run cannot even start — so a paper is never quietly
excluded from the count. A paper without pilot success is assigned exactly one failure category, decided by the
first failure in the order install → run, with the log line that decided it quoted in the pilot report.

### 6.7 Diagnosis layer: explaining a run, and the difference between two

## 7. Limitations and threats to validity

- **Small sample.** Six papers, one counted run each (the seed runs of section 6.4a are extra, not counted, runs of two papers):
  the results are anecdotal, not statistical. The
  corpus is tabular deep learning and sequence kernels, and it was corrected and reduced before the pilots (section 5.1); no
  paper was replaced because it failed (#166).
- **The run setups were written by us.** The entry command, working directory, data, build, extra requirements, and
  version constraints were chosen by Repro Radar. A paper that runs shows that it *can* be run this way, not that its
  README alone is enough. The per-paper settings were frozen for Pilot 2, so an obstacle caused by a setting (the
  read-only data mount of `paper_003`) stays in the result and was applied in Pilot 3 (section 6.1a).
- **Defects were fixed during the pilot.** The attempts ran at several Repro Radar commits. The counted runs are at two
  commits that differ only in the measurement tools (`docs/PILOT_2.md` section 12), and every earlier attempt is kept.
- **Substitutions and unpinned versions.** The CPU build of `faiss` replaces conda's CUDA build (`paper_004`), and a
  package that a requirement file leaves unpinned was installed at the newest version that fits, not the version the
  authors used.
- **Resources.** 2 CPUs, 6 GiB, 3600 seconds per phase, and no network were chosen by us; a paper that needs more fails
  here although it might run on the authors' hardware (`paper_005` at the memory limit, `paper_004` at the time limit).
  The memory re-runs (section 6.1a) show that the limit alone decided one of these: `paper_004` completed with 14265m. They
  are single runs on one machine, and the smallest sufficient limit was not searched for.
  The counted runs are CPU-only; the machine's RTX 5070 needs a PyTorch built for CUDA 12.8 or newer, which the PyTorch
  1.x pins of several papers cannot use.
- **One platform per pilot.** Pilot 1 ran on Linux runners and Pilot 2 on one Windows machine; some failures may depend
  on the platform, which is also how the Windows-only defects of the tool were found.
- **No numerical reproduction was confirmed.** Through the command line no run matched an accepted claim (claims are keyed by question
  ID, the extracted metrics by name), and aligned by hand only one real run, `paper_003`, prints a number for a claim, close to it but
  not equal (section 6.11). Tier 2 (agreement with the paper's numbers) was therefore exercised on real results only in that one
  comparison, on the synthetic control paper (section 6.4), which tests the scorer and not a paper, and on hand-made claims (section 6.9).
- **The README command mostly does not produce the paper's table.** In the automatic search no run's output matched its paper's text,
  and none of the listed candidates, at the first attempt or with repair, printed a table value of its paper (sections 6.8 and 6.10 give
  the counts). A run that completes is therefore usually not an attempt to reproduce a table, and this limits what any pilot rate says:
  it is a finding about README commands in this sandbox, not a measure of how reproducible the papers are.
- **The scorer gives a label without a comparison.** A paper with no accepted claim gets a neutral Tier 2 and can reach `Partially
  Verified` from the build tiers alone (`paper_102`, section 6.11). K2 has no positive control: the only pass among the real runs is
  by coincidence of dense numbers. Whether such a label and such a check are acceptable is a decision of the owner.
- **Stability rests on three seeds of two papers.** The seed runs of section 6.4a are not protocol runs (the CPU and memory limits
  differ from the protocol's), use three seeds each, and cover only the two papers that complete; a CV from three runs is a rough
  number, and the metric that decides Tier 3 can be a side number such as a training loss. The synthetic papers show that the
  path measures a known difference, not that a real paper is stable. Before them the repeated runs of section 6.4 (different
  memory limits or tool commits, no different seeds) showed only that the metrics repeated.
- **Field analysis.** Twelve papers from two differently chosen sub-pools, definitions written after the pilot outcomes were known,
  and an autonomy rate that counts only human actions that left a file (section 6.6): exploratory, no test, no relationship claimed.
- **Diagnosis layer.** Rule-based and tested on stored runs of this project; the hand labels are not blind, the real runs are the logs
  the rules came from, and the probes found gaps that were closed afterwards with rules written from those same lines (section 6.7). No real language model was used.
- **GPU.** One synthetic paper only; no real paper was run with the GPU, and the seed papers pin PyTorch 1.x, which the GPU cannot use.
- **External reference.** The ReScience C selection found no article that the pipeline could run (section 6.5a), so the score has no
  outside reference yet.
- **Pilot 4 is six new papers, one attempt each.** The sample came from a biased pool and drifted from tabular data, the
  README command is the first `python` line and is not always the paper's experiment (a documentation checker, a data
  preparation step), and the correction round was limited to what the logs justify, so a person with the code might have
  corrected more. The Pilot 4 rates are not comparable to the earlier pilots' rates, whose setups were prepared by hand
  (section 6.5).
- **Extended gold set without answers.** The 18 added questions have two agreeing passes but no answers from the owner,
  so no accuracy is claimed for them (section 6.4).
- **Extraction.** It is agent-assisted; the two passes are the same model, although pass B was made blind; the gold set was built from candidates listed
  by the same agent; and the quote guard proves that a quote occurs in the page text, not that the number means what the
  question asks (`docs/AGENT_EXTRACTION.md`). `paper_005`'s only accepted claim (EP300 average kernel speedup, 16) is a follow-up question that is not among the 18 gold-set questions, so it is not part of the precision and recall figures.
- **Conclusion bounds.** From these results one can say that the sandbox and the run setups made the papers installable
  and exposed what blocks each of them; one cannot say how reproducible tabular machine learning is in general.

  `docs/AGENT_EXTRACTION.md`; `docs/CORPUS_VERIFICATION.md` sections 5 and 6; `data/pilot2_runs/first_attempts/`.

## 8. Lessons learned

- **Run the tool on a second platform early.** The real-Docker acceptance checks passed in CI throughout; two defects only
  appeared on a Windows host (a CRLF entrypoint, dependency markers evaluated for the host), and several more only when
  real papers were run.
- **A conda environment file is a lock.** The first answer to the conda failures was a resolver pass over the pins
  (#227/#228); it failed on a source-only dependency and on conda's `mkl` packages. Installing the pins as they are,
  without resolving, was the correct model (#229).
- **Fix the tool, not the experiment.** Freezing the per-paper settings and allowing only fixes to Repro Radar's own code
  (`docs/PILOT_2.md` section 9) is what let a failure be told apart: the tool's defects were fixed and re-run, while the
  paper's own cache write and memory use stayed in the result.
- **Keep every attempt and say why it was replaced.** The earlier attempts show which obstacles were the tool's and which
  the papers'; the index is generated from the stored records, so the story is not retold from memory.
- **Generate the numbers and test the generation.** The generated blocks and their tests caught a stored file that
  carried a local path and a log line that a color code hid from the categorizer.
- **Label with the definitions, then look at the rules.** The hand-labeled check of the classifier (section 6.7) was labeled by
  someone who had read the rules, so it is not blind; the probes written to find gaps found them. Report both, and keep the numbers
  of the check that cannot lose.
- **A noisy side number can decide a score.** The first real seed run showed that the metric with the largest CV was a training loss;
  the summary now shows which metric decided and what each metric alone would give (section 6.4a).
- **Look at what the scorer does with real data before trusting its tests.** The tests of `cli.py score` pass because they store the
  metric under the question ID; a real run stores it under the name the extractor found, and the two never meet (section 6.11). The
  stored runs were scored only when a document asked for them.
- **What we would change next:** make the claims and the run's metrics meet (the question ID and the extracted name), choose each paper's
  command so that it produces the metrics its accepted claims name (`docs/PILOT_2.md` section 12), and find one real run whose output
  prints a table value of its paper, as a positive control for the match test (section 6.11). The four per-paper changes that
  `docs/PILOT_2.md` proposed (a writable data directory for `paper_003`, more memory for `paper_005`, more time for `paper_004`,
  `lightgbm` for `paper_002`) were applied in Pilot 3 (section 6.1a).

- **Sources:** `docs/PILOT_2.md` section 12; `data/pilot2_runs/first_attempts/README.md`; `docs/DECISIONS.md` (D-008 and
  the earlier decisions); the issues named above.
- **Status:** written.

## 9. Conclusion and future work

**What the evidence supports.** The generated
rates in sections 6.1 and 6.1a show install success, run success, and pilot success of the three pilots side by side.
A fourth pilot on six new papers, run from their README commands alone, installed fewer papers than Pilots 2 and 3 did
(section 6.5), which indicates that part of the earlier installs came from the setups written by the project; with six
papers it is an indication, not a measurement.
Part of that movement is the work on Repro Radar's own sandbox and run setups, and part of it is four per-paper
settings that were chosen after the failures were seen (section 6.1a), so it is not an improvement of the papers. The
failures that remain have named causes in the stored records: a dataset that is not accessible (`paper_008`), a request
to the OpenML API with the network off (`paper_002`), and the memory limit (`paper_004`, `paper_005`). The claim
extraction pipeline produced claims that each have a verbatim quote in the paper and an owner decision (section 6.2).
The stability tier was run on real seed runs for the first time (section 6.4a) and the diagnosis layer explains stored runs and the
difference between two (section 6.7). The dashboard of the project (`src/web/`) shows stored scores, badges, and audit reports from the database only; a fresh
database (`python cli.py init-db`) holds no score, so the dashboard shows "Not scored" for every paper until `cli.py score` is run.
`python scripts/build_demo_db.py` builds a separate database from the stored real runs, in which every paper has the score of its
best stored run (`docs/evidence/demo2/`); those scores come from the scorer through question IDs, so Tier 2 is zero for a paper with
accepted claims, and they are not validations (section 6.11).

**What the two claims rest on.** The decision on a known example (the synthetic control and the hand-made claims) is supported; the
decision on a real paper is not, because no real paper has a known answer in this work and the one real comparison is close but
unconfirmed (section 6.11). The count of papers that run is an estimate with wide intervals, not a rate.

**What it does not support.** Section 7 applies: six papers, one run each, setups written by the project, and no
confirmed numerical reproduction. One cannot say from this work how reproducible tabular machine learning is, or that the
rubric's agreement tier and stability tier work on real results.

**Future work, in the order the evidence suggests.**

1. Make the question IDs of the claims and the extracted metric names meet, choose each paper's command so that it prints the metrics
   its accepted claims name, and score such a run with `cli.py score`; this is what would exercise Tier 2 on a real result, and a run
   whose output prints a table value of its paper would also serve as the missing positive control of the match test (section 6.11).
2. Decide how much memory `paper_004` and `paper_005` need (the pilot only shows that the values chosen in advance were
   not enough) and whether `paper_002` may fetch its OpenML data.
3. Repeat the blind second pass with another model, or with the owner starting it, so that the two passes are also independent in model.
4. Run more seeds per paper, and on more papers than the two that complete, so that the stability tier (#48) rests on more than three
   runs; decide whether the metric with the largest CV should decide (section 6.4a).
5. Try the optional language-model step of the diagnosis layer with a real model, and label new, unseen failure logs to measure the
   classifier again (section 6.7: its six known gaps are closed, so the stored set no longer measures it), before anything is said about either.
6. Decide what outside reference to use for the score now that the ReScience C selection found none (section 6.5a).

### Reproducibility statement

- **Code and data.** The repository holds the code, the six-paper corpus (`data/seed_papers.json`), every stored run
  record (`data/pilot_runs/`, `data/pilot2_runs/`, `data/pilot3_runs/`, `data/pilot4_runs/`, `data/multi_seed_runs/`,
  `data/synthetic_seeds/`, `data/gpu_check/`), and the claim files (`data/claims/`). **No release
  is tagged yet** (the release issue, #45, is open), so the version of this report is the commit of the pull request
  that merges it.
- **Re-run the checks that need no Docker.** `pip install -r requirements-dev.txt`, then `pytest tests/` and
  `ruff check .`; `python scripts/report_numbers.py --check` fails if a number of this report differs from its stored
  source; `python scripts/verify_sources.py` repeats the lookups of the related-work sources (needs the network).
- **Re-run the pilots.** They need Docker. The images are built with `docker build -f docker/Dockerfile.sandbox -t repro-radar-sandbox:latest .` (`docs/ENVIRONMENT.md`; the Python 3.8 and 3.9 images use `--build-arg PYTHON_VERSION=...`), and each paper
  runs with `python scripts/run_pilot.py <paper_id>` (Pilot 2) or with `--pilot3` (Pilot 3, `docs/PILOT_3.md`). Pilot 3 ran
  on one Windows machine with Docker Desktop and WSL2 at the commit recorded in
  `data/pilot3_runs/environment.txt`. A re-run on other hardware may differ, in particular for the memory limits. The seed runs and
  the GPU check ran on the same machine (`--memory 50% --cpus 4`), and their records say that they are not protocol runs.
- **Re-run the later checks.** `python scripts/synthetic_seeds.py` (two synthetic papers, five seeds each, needs Docker),
  `python scripts/run_multi_seed.py paper_003 --pilot3 --memory 50% --cpus 4` (one real run per seed; `--summarize-only` rebuilds the
  summary from the stored folders), `python scripts/gpu_paper_check.py` (needs Docker and an NVIDIA GPU, about 3.7 GiB of wheels),
  `python cli.py diagnose <run directory>`, and, without Docker, `python scripts/field_analysis.py --check`,
  `python scripts/evaluate_diagnosis_classifier.py --check`, `python scripts/diagnosis_examples.py --check`, and
  `python scripts/diagnosis_comparisons.py --check`.
- **See the dashboard.** `python cli.py init-db`, then `python -m src.web` serves `http://127.0.0.1:8000` on the local
  machine only. With the real stored runs: `python scripts/build_demo_db.py`, then `python -m src.web --db-url
  sqlite:///data/dashboard_demo.db`. The decisions on the stored runs: `python scripts/real_verdicts.py --check` (no Docker; K2 needs the
  papers' PDFs in `data/pdfs/`, which are not committed, so only `--render` and `--check` run from the repository alone).
- **What is not reproducible from the repository alone.** The datasets that the papers download (they are fetched
  before a run, `scripts/fetch_data.py`), the live responses of Crossref and arXiv, and any result that depends on the
  speed or memory of the machine.
