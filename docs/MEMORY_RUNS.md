# Memory re-runs: Pilot 3's settings with a larger memory limit

Date: 2026-10-16. Issues #319, #321, #323, #325, #327. Records: `data/memory_runs/`. Table: `scripts/memory_runs.py`.

## 1. What was run, and what these runs are not

Three papers were run again with exactly the per-paper settings of Pilot 3 (`data/pilot3_settings.json`, `--pilot3`) and one
change: the memory limit (and the equal swap limit) was `50%` of the host's RAM instead of the protocol's value.

```
python scripts/run_pilot.py <paper_id> --pilot3 --memory 50% --record-root data/memory_runs
```

The share resolves to `14265m` on the machine used (`src/sandbox/resources.py` caps a share at 90 percent of the memory
that Docker itself sees; the record keeps the request, the resolved size, and the protocol's limit as `memory_override`).
The runs were made one after the other on one Windows machine with Docker Desktop (Docker 29.8.2, 12 CPUs).

**These are not protocol runs.** The pilots' limits are fixed in `docs/PILOT_2.md` and `docs/PILOT_3.md`; the memory limit
here differs, so the records are kept apart (`data/memory_runs/`), `data/pilot2_runs/` and `data/pilot3_runs/` were not
touched, and no rate of the report was recomputed from them. Each paper was run once; a run that failed was kept as it
ended and not repeated. None of the runs is scored against a claim.

## 3. Did the papers run?

- **`paper_003`: yes, as in Pilot 3.** Both runs completed with exit code 0. The final lines are the same (train rmse 0.363,
  validation rmse 0.473, test rmse 0.473), and `stdout.log` is identical line by line once the epoch clock times and the
  line endings are ignored. `scripts/hash_run.py --compare` reports no byte-identical log or metadata file (clock times,
  durations, and paths differ; `data/memory_runs/paper_003/hash_compare.txt`). The paper did not need more than the
  protocol's 6 GiB (peak about 1.1 GiB in both runs).
- **`paper_004`: yes, with the larger limit.** It completed with exit code 0 after about 2 h 33 min; Pilot 3 had ended it
  as OOM_KILLED at the 6 GiB limit. The peak was 10.64 GiB, above the protocol's 6 GiB and below Pilot 3's choice for
  `paper_005` of 12 GiB. The paper's own last output has `'test': -0.3994...` for its california configuration; **this is
  the log's value and not a result of this project**: no accepted claim of `paper_004` was compared with it.
- **`paper_005`: no.** It was killed again (OOM_KILLED, exit code 137), at step 187 of 540 of the grid search, further
  than with 12 GiB (step 161) and with 6 GiB in Pilot 2 (step 76), and the peak reached the limit. A larger limit moved
  the kill later but did not remove it. The records do not show how much memory the whole grid needs or why the use grows;
  the next step is the owner's decision (a larger limit, a smaller grid, or leaving the paper out).

## 4. What this says about the sandbox's memory limit

- The limit is a hard cap in both directions that the records show. When the limit was too small, the container was killed
  with exit code 137 and the status OOM_KILLED, with `killed_before_timeout` false and the peak equal to the limit
  (`paper_005` in both of its runs; `paper_004` in Pilot 3). When the limit was large enough, the same run completed
  (`paper_004` here).
- So the OOM_KILLED results of `paper_004` in Pilot 3 were caused by the 6 GiB limit that the protocol set, not by the paper's
  code failing; the larger limit changed the outcome of this paper and not of `paper_005`.
- The memory limit is one of the settings that decides the pilot's rates (`docs/report/REPORT.md`, sections 6.1a and 7); the rates
  of the report still describe the protocol runs.

## 5. Limits of this evidence

- One run per paper and limit; no repetition, so run-to-run variation of the peak is unknown.
- The smallest sufficient limit was not searched for: `paper_004` needed at most 14265m and at least what it used (10.64 GiB).
- Only `paper_003`'s output was compared with Pilot 3's (stdout after normalizing); the other logs differ in clock times
  and were not compared further.
- The peak is the sandbox's own measurement; it was not checked against another tool.
- The machine, Docker version, and share cap are those of one Windows host; a Linux host was not tried.
